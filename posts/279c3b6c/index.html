向量KNN-BM25-RRF融合

先看两个会翻车的查询。

查询一：ERR_CONN_REFUSED 怎么解决。纯向量检索很可能返回一堆讲”网络连接失败”的泛泛文章——语义是对的，但错误码没对上。用户要的是精确提到这个字符串的那一页。

查询二：笔记本充不进电。纯 BM25 可能漏掉标题是”电池无法充电”的文档——没有一个共同词，词法匹配直接归零。

两个检索器的失败方向正好相反：BM25 在”字面没对上”时挂掉，向量检索在”语义糊了、细节丢了”时挂掉。所以工业界的标准做法不是二选一，而是各取 top 50，再用 Reciprocal Rank Fusion（RRF）把两份排名合成一份。这篇文章讲清楚三件事：各自怎么工作、为什么不能直接加分数、RRF 为什么是默认答案，以及它什么时候不灵。

BM25：词匹配的底线

BM25 上世纪九十年代在 Okapi 系统里成形，是 Elasticsearch/Lucene 的默认打分函数。它只做一件事：统计查询词在文档里出现了多少次，然后打折扣。三个机制值得记住：

  1. 词频饱和（$k_1$）：一个词从出现 1 次到 2 次，分数涨很多；从 20 次到 21 次，几乎不涨。避免关键词堆砌刷分。
  2. 文档长度归一化（$b$）：长文档天然词多，要压一压。$b=0.75$ 时压 75%，$b=0$ 完全不压。
  3. 逆文档频率（IDF）：”的”这种到处都有的词权重趋近于零，罕见词权重高。”CVE-2024-3094”这种字符串的 IDF 会非常高。

公式（BM25 打分）：

$$
\mathrm{score}(q,d)=\sum_{t\in q}\mathrm{IDF}(t)\cdot\frac{f(t,d),(k_1+1)}{f(t,d)+k_1\left(1-b+b\cdot\frac{|d|}{\mathrm{avgdl}}\right)}
$$

$$
\mathrm{IDF}(t)=\ln\left(1+\frac{N-n_t+0.5}{n_t+0.5}\right)
$$

第二个式子是 Lucene 变体，对数里加 1 避免 IDF 出现负值。常用参数：$k_1 \in [1.2, 2.0]$，$b = 0.75$。其中 $|d|$ 是文档长度，$\mathrm{avgdl}$ 是平均文档长度，$N$ 是文档总数，$n_t$ 是包含词 $t$ 的文档数。

BM25 的优势几乎都来自”不需要训练”：

  • 零样本可用，新领域、新语言只要有分词器就能跑；
  • 精确字符串、编号、错误码、人名、型号，一个不漏；
  • 分数可解释：这个词贡献多少、IDF 多少，都能拆开看；
  • 便宜：CPU 内存索引，毫秒级。

它的缺陷同样明确：

  • 词汇鸿沟：查询说”充不进电”，文档说”无法充电”，一个词没对上就是零分；
  • 同义、缩写、拼写变体全靠 analyzer 兜底（同义词表、词干化），维护成本高；
  • 中文需要分词，jieba/IK 的分词粒度直接决定召回质量，”南京市长江大桥”这类切分歧义很难根治；
  • 完全不懂语序和上下文，”苹果”是水果还是公司，它不知道。

向量 KNN：语义的近邻

向量检索把文本变成一串数字，然后找距离最近的邻居。

流程是固定的：切块（chunk）→ embedding 模型编码 → 写入向量索引 → 查询编码成同空间向量 → 找 top-k 最近邻。

工程上要区分两件事。

精确 KNN 与近似 KNN。 精确 KNN 是暴力遍历：100 万条 768 维向量，每次查询要算 7.68 亿次乘加，延迟和成本都不可接受。实际用的是近似最近邻（ANN），主流是 HNSW：多层图结构，上层稀疏负责快速跳转，底层稠密负责精确定位，查询时从顶层贪心往下走。ef_search 控制候选队列大小——调大召回率上升、延迟上升，这是必须显式做的取舍。其他方案还有 IVF（聚类分桶）、PQ（乘积量化压缩内存），常和 HNSW 组合使用。

相似度度量。 余弦相似度、内积、欧氏距离。用内积检索时先把向量归一化，否则向量模长会偷偷影响排序；模型训练时用什么度量，索引就该用什么度量。

向量检索赢在语义：换一种说法、跨语言、模糊描述，它都能找到。它输在细节：

  • 错误码、编号、SKU、人名，embedding 经常”看着像”就放行；
  • 领域漂移：通用 embedding 模型在医疗、法律、代码仓里的表现可能不如 BM25。BEIR 的结论很直白——稠密模型在域内强，零样本跨域时 BM25 是极难打败的基线；
  • 相似不等于正确：语义最近的文档可能恰好是错误答案，ANN 只保证”近”，不保证”对”；
  • embedding 模型换版本要全量重建索引，这是实实在在的运维债。

为什么不能把两个分数直接相加

最直觉的做法是 0.5 * bm25 + 0.5 * cosine，大多数时候会翻车，原因有三个：

  1. 量纲不同。 BM25 分数无上界，一次查询里 top1 可能是 35，另一次可能只有 8；余弦相似度被压在 $[-1,1]$。固定权重没有意义。
  2. 分布随查询变化。 同一个 BM25 索引，查询”的”和查询”CVE-2024-3094”，分数分布完全不一样。做 min-max 归一化，min 和 max 都是当前候选集里算出来的，候选一变，归一化结果就变。
  3. 分数不可比。 要让两个检索器的分数可比，需要标注数据做校准（calibration），这违背了”开箱即用”的初衷。

所以工业界默认用排名而不是分数做融合。排名是天然的归一化：不管 BM25 打 35 分还是 8 分，第一名就是第一名。

RRF：只信排名的融合

RRF 来自 Cormack、Clarke 和 Büttcher 2009 年的 SIGIR 论文《Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods》。公式只有一行：

$$
\mathrm{RRF}(d)=\sum_{i=1}^{m}\frac{w_i}{k+\mathrm{rank}_i(d)}
$$

  • $\mathrm{rank}_i(d)$：文档 $d$ 在第 $i$ 路检索结果里的名次，从 1 开始；
  • 没出现在某一路结果里，这一路就不贡献分数；
  • $w_i$ 是第 $i$ 路的权重，等权时全为 1；$k$ 是平滑常数，论文用的 $k=60$，大多数系统沿用它作为默认值。

看一个具体例子。BM25 和向量检索各返回 top 5：

文档 BM25 名次 向量名次 RRF 分数（$k=60$）
D2 2 1 $\frac{1}{62}+\frac{1}{61}=0.03252$
D1 1 3 $\frac{1}{61}+\frac{1}{63}=0.03227$
D3 3 4 $\frac{1}{63}+\frac{1}{64}=0.03150$
D6 — 2 $\frac{1}{62}=0.01613$
D4 4 — $\frac{1}{64}=0.01563$
D5 5 — $\frac{1}{65}=0.01538$
D7 — 5 $\frac{1}{65}=0.01538$

这个表说明了 RRF 的核心性质：两路都靠前的文档，赢过只在单路第一的文档。D2 在 BM25 只是第二，但它同时被两路认可，压过了 BM25 第一的 D1。这正是我们要的”共识”——单个检索器的第一名可能是噪声，两个独立系统同时给出的高分更可信。D5 和 D7 打平，RRF 本身不提供打破平局的信息，实际系统需要按次级信号（原始分数、时间、点击率）兜底。

$k$ 的作用是压平头部。$k=60$ 时，第 1 名和第 2 名的贡献比是 $62:61$，差距很小；如果 $k=0$，第一名权重 1.0、第二名 0.5，头部会极端主导。$k$ 越大，融合越”民主”，越依赖多路共识；$k$ 越小，越接近”谁的第一名谁说了算”。没有普适最优，只有用评估集调出来的值。

RRF 的适用场景很好判断：

  • 两路检索器的分数不可比、分布不稳定——RRF 正合适；
  • 没有标注数据做校准——RRF 不需要训练；
  • 想要一个能直接上线的默认方案——RRF 参数只有一个 k，几乎不用调。

最小实现

核心逻辑十行以内：

def rrf_fuse(rankings: list[list[str]], k: int = 60,
             weights: list[float] | None = None) -> list[tuple[str, float]]:
    """rankings: 每路检索器返回的文档 id 列表，按相关度降序。"""
    weights = weights or [1.0] * len(rankings)
    scores: dict[str, float] = {}
    for weight, ranking in zip(weights, rankings):
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + weight / (k + rank)
    return sorted(scores.items(), key=lambda item: item[1], reverse=True)


bm25_hits = ["D1", "D2", "D3", "D4", "D5"]
vector_hits = ["D2", "D6", "D1", "D3", "D7"]
fused = rrf_fuse([bm25_hits, vector_hits])

真实系统里，这段逻辑通常不用自己写。Elasticsearch 8.x 提供了 rrf retriever，把 standard 查询和 knn 查询包在一起，用 rank_constant 和 rank_window_size 控制融合窗口（下面为示意，向量维度做了截断，字段名以你使用的版本为准）：

POST /_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        { "standard": { "query": { "match": { "content": "ERR_CONN_REFUSED" } } } },
        {
          "knn": {
            "field": "embedding",
            "query_vector": [0.12, -0.03, 0.08],
            "k": 50,
            "num_candidates": 200
          }
        }
      ],
      "rank_constant": 60,
      "rank_window_size": 50
    }

}

OpenSearch、Qdrant、Weaviate、Milvus 也都内置了 RRF 或类似的排名融合（有的叫 fusion，有的叫 hybrid query，参数名各不相同，语义一致）。如果用的是 pgvector + tsvector（或 BM25 扩展）这类自己拼的方案，上面那个函数就是全部融合逻辑。

上线前要想清楚的几件事

候选深度。 每路先取多少条再融合？取太少，RRF 没有素材；取太多，尾部噪声进入融合。经验值每路 top 50–100，融合后取 top 20–50 交给下一级精排。

融合之后还要精排。 RRF 只解决”合并”，不解决”精准”。标准管线是：BM25 + 向量召回 → RRF 融合 → cross-encoder 重排（对 top 20–50 逐条打分）→ 送进 LLM。重排模型看得到 query 和文档的完整交互，是精度提升最大的一环，但延迟也最高，所以只放在小候选集上。

粒度要对齐。 BM25 按 chunk 建索引，向量也按 chunk 建索引，两路的 doc_id 才能对齐。如果一路按文档、一路按 chunk，融合前要做 id 映射，否则同一份内容会被当成两个文档各算各的。文档级去重放在融合之后：同一文档的多个 chunk 命中，只保留最高分那个。

中文分词。 BM25 那一路的 analyzer 决定一切。jieba/IK 加领域词典（产品名、错误码、内部术语），比换 embedding 模型便宜得多，收益却常常更大。

权重。 默认等权。当你知道某一路明显更强（比如领域内微调过的 embedding），用加权 RRF：$\frac{w_i}{k+\mathrm{rank}_i(d)}$，即给该路更大的 $w_i$。权重不要拍脑袋，用评估集说话。

评估。 建一个 50–200 条查询的小金标集，覆盖两类查询：精确标识符类（错误码、型号、人名）和自然语言描述类。分别测 BM25-only、向量-only、RRF 三组，看 recall@50（召回阶段）和 nDCG@10 / MRR（最终排序）。按查询类型拆开看——RRF 的平均分可能只涨两个点，但精确标识符类查询的涨幅可能是二十个点，这才是它真正的价值。BEIR 这类公开 benchmark 可以给你方向感，但不能替代你自己的数据。

RRF 什么时候不灵。 三种情况：一路检索器显著强于另一路，等权融合会拖后腿（加权或直接不用融合）；两路高度相关（比如同一个 embedding 模型的两个版本），共识没有信息量；你需要保留分数差距做阈值过滤（RRF 把所有排名差压成固定值，高分文档和低分文档在融合后可能只差 0.001）。

收尾

记住三件事就够了：

  • BM25 保下限：精确词、罕见词、标识符，它不会漏；
  • 向量 KNN 抬上限：换说法、跨语言、模糊意图，它能找到；
  • RRF 做缝合：只信排名不信分数，一个参数 k，几乎零调参成本。

这套组合不是最先进的，但它是到 2026 年仍然最稳的默认答案。真正拉开差距的从来不是融合公式，而是候选深度、分块策略、重排模型，以及那套属于你自己业务的小金标集。
